# Telemetry vs. the asset-pipeline decision (#339 / #371 / #380) — a skeptical evaluation

## 1. What is actually being decided in #380

**#380** (`jsteinich`, "Asset pipeline scope") frames exactly two questions: *"**How much belongs in the core `cdktn` library**, versus in standalone packages or in the higher-level construct libraries"* and *"**When each part runs** — synth, plan, or apply."* The stated reason both are urgent: *"Everything public in `cdktn` goes through JSII to TypeScript, Python, Go, Java, and C#, so the API surface is expensive to change once released."*

**Phase model (essentially settled).** jsteinich argues AWS CDK's shape does not transfer because it is forced by two CloudFormation properties, and *"**Terraform has neither property.** Providers read local files directly … Adopting CDK's structure would mean paying its costs without having its constraints."* The proposal: *"**Build and bundle at synth.** This isn't merely permitted, it's required: `plan` can only produce an honest diff if the artifact's identity is already fixed when it runs"*; *"**Publish at apply**, as ordinary Terraform resources"*; *"**No new CLI phase.**"* `eduardomourar` agrees flatly: *"I agree with the phase model — build-at-synth / publish-at-apply is the right shape for Terraform, and no new CLI phase keeps things simple."* This resolves the fork `sakul-learning` opened on #339 (*"**Terraform-managed publication** … or is the long-term plan a CDKTN publisher that performs those side effects directly?"*), which eduardomourar had already answered *"**Terraform-managed publication** is the intended model."*

**Core/non-core split (agreed in principle).** Core keeps identity, staging, `IAssetBundler`, `IAssetPublisher`; bundlers go to `@cdktn/bundler-*`, publishers to cloud construct libraries, AWS CDK asset vocabulary to a compatibility layer. eduardomourar: *"**Small core:** agreed. Docker bundling doesn't belong in core."*

**The interface delta (jsteinich, 5520286050)** is where the live decisions are: `FileAssetPackaging` enum → `IAssetPackaging` (*"a closed enum can't express anything but zip"*), `packaging` → `isDirectory` on `StagedAsset`, new `AssetHash.of()` (identity without staging), new `IIgnoreStrategy`. Evidence cited is almost entirely *structural*, not empirical: a jsii error (`JSII5015: Interface "IS3AssetPublisher" re-declares member "publish"` — *"verified by compiling it"*), a fact about the shipped code (*"`AssetType.DIRECTORY` maps to `copySync` in `TerraformAsset` today — so a two-value enum is narrower than shipped behaviour"*), and a correctness argument (*"**Bundling isn't always deterministic** … a source-hash-only design shows no diff while the artifact has actually changed"*).

**The one piece of user evidence is n=1.** `garysassano` (5386369510) supplies the only field report: *"I have a stack where the Docker provider builds an image from a source directory … `TerraformAsset` can't serve this. `assetHash` is exposed, but obtaining it means copying the whole tree into the synth output for a copy I then discard … I ended up reimplementing `hashPath` with a `.dockerignore`-shaped ignore list."* His two questions — *"**Will exclusion be expressible through the public API**"* and *"**Is 'content identity without staging' in scope?**"* — were both answered yes, and directly produced `AssetHash.of()` and `IIgnoreStrategy` in the delta and in #371. One user comment moved two public API items. The other evidence is anecdote: eduardomourar, *"running my team's deployment using TerraConstructs in Production for the past 7 months … multiple Lambda functions … that have zip files from S3"*; so0k pointing at TerraConstructs source links when jsteinich asked for user stories.

**What is still unresolved.** jsteinich's own list: container images (*"**Input especially welcome here**"*), shared artifacts across stacks, cleanup of superseded artifacts, and *"**Does the base `IAssetPublisher` earn its place**"*. Plus one blocked item from eduardomourar's prototype (5546990854): *"added isDirectory but kept packaging too. **No real consumer to force the cut yet since the publisher pipeline isn't built** … Only real open item is your item 2, and it's blocked on the rest of #380."* And a perf wrinkle: a custom `IIgnoreStrategy` *"can't go in that key. Had to skip the cache entirely"* — partly mitigated in #371 by `cacheKey?: string`.

**The sentence that invites telemetry.** jsteinich on #339 (5016795051): *"Would be nice to have some user stores and/or specific deployment patterns to use in guiding the planning and development."* That is the only request in the whole thread that usage data could plausibly serve — and note it asks for *stories and patterns*, not counts.

**#371** is now scoped as the foundation slice for the above; its review threads (jsteinich ↔ eduardomourar, ids 3940542834/837/840/841, 3941747273) are all API-correctness arguments — `pack()` must take a `PackOptions` struct because *"adding struct fields is additive while adding method parameters is not"*, `AssetHash.of()` must pin `canonical: true` because *"a brand-new public API has no existing hashes to preserve"*, a test that *"passes with or without `canonical: true`"*. None of these has an empirical component at all.

## 2. Decision-relevant questions telemetry could answer

| # | Question | Metric + attributes | Privacy | What it cannot tell us |
|---|---|---|---|---|
| Q1 | Does anyone use `TerraformAsset` at all, and file vs directory vs archive? | `cli.stack.asset` count; attrs: existing base set + `packaging` (`file`\|`directory`\|`zip`) | Fine — 3-value enum | Nothing about *why*, nothing about whether they wanted bundling, publishing, or just a path. Requires a **library change** (§3). |
| Q2 | Do users already hand-roll publishing today? | `cli.stack.resource` count; attr `resource_type` restricted to an allow-list (`aws_s3_object`, `aws_s3_bucket_object`, `docker_image`, `docker_registry_image`, `terraform_data`, `null_resource`, `azurerm_storage_blob`, `google_storage_bucket_object`) | Fine — resource types are already sent as `resource_type` on `cli.stack.override` | Cannot distinguish "publishing an asset" from "managing an unrelated object". `terraform_data`/`null_resource` are wildly overloaded. No library change needed (§3). |
| Q3 | Which clouds would need publishers — i.e. is "publishers live in the cloud libraries" a burden on one library or five? | **Already shipped in #62**: `cli.stack.provider` (`provider`, `binding`, `version_constraint`) | Already vetted | Provider presence ≠ asset need. An `aws` user with no Lambda needs no publisher. |
| Q4 | Is synth predominantly CI or interactive (bears on level-1 "external pipeline publishes" and on "Docker on the apply machine")? | **Already shipped**: `ci` attribute on every metric | Already vetted | Meaningless unless cross-cut by Q1/Q2, i.e. useless on its own. |
| Q5 | Asset sizes / build durations (bears on "moving the image between phases … isn't practical at realistic sizes") | `cli.asset.size` distribution, bucketed | Byte counts are enumerable-safe | Would only ever measure *file* assets that already work; says nothing about image sizes, which is the actual open question. |

Deliberately **not** proposed: exclusion-pattern shapes, hash-type mix (`SOURCE`/`OUTPUT`/`CUSTOM`), bundler images. The first two are unobservable until #339/#371 ship the options; the third (`image` on `DockerImage.fromRegistry`) is user-controlled free text and would be a cardinality and privacy hazard.

## 3. Where telemetry would be misleading or insufficient

**Selection bias is severe and asymmetric.** Effective consent (spec FR-016/FR-017): `CHECKPOINT_DISABLE` wins, then explicit `sendUsageTelemetry`, then an interactive one-time prompt, then default-on non-interactive. So the population that reports is *non-interactive runs that nobody disabled* plus *interactive users who said yes to a prompt*. The project's own CI sets `CHECKPOINT_DISABLE` in *"13 locations across 6 files"* (spec, OS-001) — and that is precisely the CI-heavy, asset-heavy usage pattern #380 cares about. Corporate egress blocks and air-gapped runners subtract more of the same population. Emission also requires a baked `SENTRY_DSN`, so anyone building the CLI from source reports nothing. The users most likely to have a sophisticated asset pipeline are the users least likely to be measured.

**You cannot observe a feature that does not exist.** #380 is deciding the shape of a pipeline that has not shipped. Every asset metric measures `TerraformAsset` as it is today — a feature garysassano describes as unusable for his case. Absence of `TerraformAsset` usage is equally consistent with "nobody needs assets" and with "the current asset support is too weak to use, so people hand-roll" — his comment is direct evidence of the latter. A near-zero count would therefore be *unfalsifiable* as an argument for a small core.

**Timeline lag makes the data arrive after the decision.** #380's substantive comments run 2026-08-23 → 2026-09-04; #371 was declared *"ready for review now fully based on the discussed from #380"* on 2026-09-05. #62 is still **open**. Adding a metric to #62 means: merge #62 → cut a release → users upgrade → accumulate a usable sample. That is quarters, not weeks, and the JSII surface #380 is arguing about will be frozen long before. Any recommendation framed as "let's get data first" is, in practice, a proposal to defer #380 indefinitely — a maintainer would be right to reject it on that ground alone.

**Cardinality.** Attributes multiply combinatorially against the base set already attached to every metric (`command`, `ci`, `os`, `arch`, `target_terraform`, `target_opentofu`, `binary`, `binary_version`, `language`). `cli.stack.provider` already emits one series per provider per constraint per version. An unrestricted `resource_type` attribute (thousands of AWS resource types) crossed with that base set is a genuine explosion; the allow-list in Q2 is not optional. The sponsored plan's quota is generous in *volume*, which is not the same as tolerant of *series count* — and the research notes only ever confirmed trace-quota independence, never a cardinality budget.

**Library vs CLI — the load-bearing structural constraint.** The metrics live in `packages/@cdktn/commons/src/telemetry.ts` and are called from the CLI. The only library→CLI channel is `SynthStack.telemetryPayload` (`packages/@cdktn/cli-core/src/lib/synth-stack.ts:288-302`), which reduces each stack to `c?.["//"]?.metadata` and `c?.terraform?.required_providers`. That metadata block is built in `packages/cdktn/src/terraform-stack.ts:480-516` from `TerraformStackMetadata` merged with `elements.map((e) => e.toMetadata())`, where `elements = terraformElements(this)` — i.e. **`TerraformElement`s only**. `TerraformAsset extends Construct` (`packages/cdktn/src/terraform-asset.ts:41`) and has no `toMetadata()`. **Assets are structurally invisible to telemetry today.**

To surface Q1, the library would have to contribute an `assets` group to the metadata block, following the `imports`/`moved` precedent at `packages/cdktn/src/terraform-resource.ts:447` (which the CLI already reduces to counts via `groupSizes()`, never sending names). Is that acceptable? **Partly, and it should not be done for telemetry's sake.** `"//".metadata` is not a private channel — it is user-visible synthesized output that people read, commit, and diff. Adding a group changes every synthesized `cdk.tf.json` for asset users (snapshot churn across the repo and downstream libraries), and it is a jsii-visible behavior change landing in the exact package #380 is trying to keep small. It would have to be justified as *product* metadata (something the CLI or a future `cdktn assets` command genuinely needs, e.g. jsteinich's level-1 manifest) with telemetry as a side effect. Instrumenting `cdktn` to feed a metric is the tail wagging the dog, and a maintainer applying #380's own "small core" logic should say no.

There is one blind spot even for the CLI-side option: when a stack synthesizes to HCL rather than `.tf.json`, `synth-stack.ts:266-269` reads only the separate metadata file, so `resource` keys are unavailable. Q2 would silently under-count HCL projects.

## 4. Recommendation

**Add two things, both CLI-side, both cheap; add nothing to the library.**

1. **`cli.stack.resource`** — count, attrs: base set + `resource_type` from a hard-coded ~10-entry publishing-related allow-list, everything else dropped. Emission point: `sendStackTelemetry` in `telemetry.ts`, fed by extending `SynthStack.telemetryPayload` with `Object.keys(c?.resource ?? {})`. **No library change** — the parsed stack JSON is already in hand there and is deliberately narrowed. *Confidence it would change a #380 decision: **low (~20%)**.* It is the best available proxy for "users hand-roll publishing", which bears on whether level 0/1 opt-outs are the common case rather than the exotic one. *Why a maintainer would disagree:* `terraform_data` and `null_resource` are too overloaded to interpret, the allow-list bakes in a guess about which clouds matter, and it adds a new payload field to a function whose docstring explicitly says *"Resource config and outputs stay out of the payload."*
2. **Nothing new for provider mix or CI split** — `cli.stack.provider` and the `ci` attribute already ship in #62 and already answer Q3/Q4 as well as they can be answered. *Confidence: high that they are worth having, low that they will be decisive for #380.*

**Explicitly do not add** a `cli.stack.asset` metric in this cycle. It requires a library change to `"//".metadata` (§3), it measures a feature that is about to be replaced, and it cannot arrive before #380 closes. Revisit it *after* the pipeline ships, when `packaging`, `bundled`, and `hash_type` describe something real and the numbers can inform the *second* round of API decisions (defaults, whether `AUTO_DISCOVER` earns its keep, whether `AssetPackaging.DIRECTORY` is used).

**Questions in #380 that telemetry cannot touch, at any sample size:**
- The phase model. It is derived from Terraform's semantics and from the requirement that `plan` produce an honest diff. No usage count can contradict it.
- The core/non-core split. This is a JSII-cost and API-design judgment.
- The sibling-vs-hierarchy interface shape. `JSII5015` is a compiler fact.
- The container-image phase question. jsteinich asked for *"input"*, and eduardomourar deferred images entirely; what is needed is a handful of interviews with people who run Docker builds in CI (garysassano is the obvious first call), not a counter.
- Shared artifacts, cleanup, and whether `AssetReference` should ever carry destination-assigned values. All correctness/ownership arguments.
- Whether `isDirectory` can replace `packaging` — eduardomourar's own answer is that it is blocked on *a consumer existing*, not on evidence of demand.

**Honest bottom line: telemetry contributes very little to #380, and it would be dishonest to claim otherwise.** Every load-bearing argument in the thread is structural (jsii constraints, Terraform's execution model, hash/artifact drift) or is a single well-argued user report. The one thing usage data could genuinely have supplied — jsteinich's request for deployment patterns — is a qualitative question that a count answers badly and an interview answers well. The defensible reason to add metric (1) is not that it will settle #380; it is that it is nearly free, it is CLI-side, and it builds a baseline for the *post-ship* questions. If the choice is between shipping #371 now and waiting for numbers, ship #371.
